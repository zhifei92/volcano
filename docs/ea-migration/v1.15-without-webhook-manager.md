# v1.15.3 不部署 webhook-manager 能否正常工作

> 基于社区 v1.15.3 源码（`git archive v1.15.3`）和内部分支 `origin/gpu-numa` 的部署配置分析。文中代码路径均相对 v1.15.3 仓库根目录。

## 1. 结论

**能跑，但有前提。** scheduler 和 controller-manager 都不依赖 webhook-manager 进程，不部署它，两个组件照常启动和调度。

webhook-manager 本身只做一件事：给 webhook 配置填 caBundle 并提供 HTTPS 服务（`cmd/webhook-manager/app/server.go`）。去掉它真正的风险在两处：

1. 只删 webhook-manager、不删 webhook 配置时，apiserver 仍会去调用它，命中的创建请求全部失败（见第 2 节）；
2. mutate webhook 原本补的默认值没人补了，其中几个字段 controller 没有兜底。

## 2. 前提一：webhook 配置必须一并去掉

webhook 分两部分，生命周期互相独立：

- **webhook 配置**：MutatingWebhookConfiguration / ValidatingWebhookConfiguration，是存在 apiserver（etcd）里的 K8s 对象，告诉 apiserver "创建哪类资源时要先调用哪个 Service"。v1.15 里这些对象由 Helm 模板 `templates/webhooks.yaml` 创建，webhook-manager 启动时只负责把 caBundle 填进去（`cmd/webhook-manager/app/util.go`）。
- **webhook-manager**：真正处理请求的 HTTPS 服务，背后是 `volcano-admission-service`。

所以只删 webhook-manager 的 Deployment，这些配置对象还留在 apiserver 上，这就是所谓"残留"。之后的请求流程是：

```
kubectl create vcjob
  → apiserver 发现命中 webhook 配置，去调 volcano-admission-service
  → Service 没有后端，连接失败或超时（timeoutSeconds: 10）
  → failurePolicy: Fail，apiserver 直接拒绝请求
  → 报错：failed calling webhook "mutatejob.volcano.sh": ... connection refused / no endpoints available
```

社区 chart 里所有 webhook 都是 `failurePolicy: Fail`，因此 vcjob、Queue、PodGroup 的创建都会被拒。如果像内部线上那样开了 `/pods/mutate`、`/pods/validate`，命中范围是**集群里所有 Pod 的创建**，影响面最大。

（`failurePolicy: Ignore` 才是"调不通就放行"。改成 Ignore 能避免请求被拒，但默认值和校验照样没有，等价于没部署，不推荐靠它绕过。）

处理方法：

- 用 Helm 部署：设置 `custom.admission_enable: false`，整个 `webhooks.yaml` 和 admission 相关资源都不会渲染。
- 自己写 manifest：不要创建 webhook 配置，也不要跑 admission init job（生成证书的 Job）。
- 从已有部署下线：先删 webhook 配置，再删 webhook-manager。可以用 `kubectl get mutatingwebhookconfigurations,validatingwebhookconfigurations | grep volcano` 确认已经删干净。

### 2.1 k8s 1.19 上 Pod webhook 的额外风险

chart 里 Pod webhook 想用 namespaceSelector 排除 `kube-system` 和 volcano 自己的 namespace：

```yaml
namespaceSelector:
  matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: NotIn
      values: [volcano-system, kube-system]
```

但 `kubernetes.io/metadata.name` 这个 label 是 k8s 1.21 起才由 apiserver 自动给 namespace 加上的，1.19 上默认没有。label 不存在时 `NotIn` 判定为命中，**排除条件失效，kube-system 和 volcano-system 的 Pod 也会走 webhook**。

这样一来，webhook-manager 挂掉时，kube-system 里的 Pod 也建不出来，webhook-manager 自己的 Pod 也重建不了（创建它也要先调它自己），形成死锁，只能手动删 webhook 配置解围。

如果在 1.19 上保留 Pod webhook，部署前给所有 namespace 手动补上这个 label：

```bash
for ns in $(kubectl get ns -o name | cut -d/ -f2); do
  kubectl label ns "$ns" kubernetes.io/metadata.name="$ns" --overwrite
done
```

新建 namespace 时也要补，或者改用 `webhooks_namespace_selector_expressions` 配一个你们自己维护的 label。

## 3. 前提二：提交 vcjob 时，客户端必须把字段写全

不同类型的对象受影响程度不一样：

- **vcjob 影响最大。** `jobs/mutate`（`pkg/webhooks/admission/jobs/mutate/mutate_job.go`）只在 CREATE 时补默认值，而 controller 对其中几个字段没有兜底。
- **普通 Pod / Deployment** 只要 `schedulerName: volcano`，由 podgroup controller 自动建 PodGroup，基本不受影响。PodGroup 的 queue 为空时，scheduler 会回落到 default 队列：

```go
// pkg/scheduler/cache/event_handlers.go:843
// TODO(k82cn): set default queue in admission.
if len(ss.Spec.Queue) == 0 {
	sc.Jobs[job].Queue = schedulingapi.QueueID(sc.defaultQueue)
}
```

### 3.1 缺少 jobs/mutate 时 vcjob 各字段的后果

| 不写的字段 | 原本由 webhook 补成 | 不补的后果 |
|---|---|---|
| `spec.schedulerName` | `volcano` | **Pod 交给 kube-scheduler 调度，gang 完全失效**（见 3.2） |
| `spec.queue` | `default` | **job controller 执行 `GetQueueInfo("")` 失败，syncJob 一直报错，作业卡住不建 Pod**（见 3.2） |
| `spec.minAvailable` | 各 task 的 minAvailable 之和 | PodGroup 的 minMember=0，gang 等于没开，会部分调度 |
| `spec.maxRetry` | 3（`DefaultMaxRetry`） | 等于 0：restarting 状态里 `RetryCount >= 0` 立即成立，**任何 RestartJob 策略都会直接把作业判为 Failed**（见 3.2） |
| `tasks[].name` | `default0`、`default1`… | Pod 名变成 `<job>--0`；多个 task 名字都为空时 Pod 名冲突 |
| `tasks[].minAvailable` | replicas | controller 有兜底（`getMinTaskMember`），无影响 |
| mpi / pytorch / tf / ray 的 `svc`、`ssh` 插件 | 自动补上 | 不写就没有 headless svc 和 ssh 互信，分布式作业起不来 |
| hostNetwork 时的 dnsPolicy | `ClusterFirstWithHostNet` | Pod 内无法解析集群 DNS |

### 3.2 关键代码依据

schedulerName：controller 只在 Pod 模板没写时用 job 的值，job 的值也为空，apiserver 就会默认成 `default-scheduler`。

```go
// pkg/controllers/job/job_controller_util.go:63
if len(pod.Spec.SchedulerName) == 0 {
	pod.Spec.SchedulerName = job.Spec.SchedulerName
}
```

queue：syncJob 一开始就按 `job.Spec.Queue` 查队列，空字符串查不到，直接返回错误，后面的建 PodGroup、建 Pod 都不会执行。

```go
// pkg/controllers/job/job_controller_actions.go:359
queueInfo, err := cc.GetQueueInfo(job.Spec.Queue)
if err != nil {
	return err
}
```

maxRetry：为 0 时，killJob 里每次都被当作最后一次重试，restarting 状态第一次进入就判 Failed。

```go
// pkg/controllers/job/state/restarting.go:31
maxRetry := ps.job.Job.Spec.MaxRetry
if status.RetryCount >= maxRetry {
	status.State.Phase = vcbatch.Failed
	...
}
```

### 3.3 缺少 queues/mutate 时 Queue 的变化

`queues/mutate`（`pkg/webhooks/admission/queues/mutate/mutate_queue.go`）补三项：

- 层级注解加 `root/` 前缀：不用层级队列的话无影响。
- `reclaimable` 为 nil 时补成 true：scheduler 本来就按 true 处理（`pkg/scheduler/api/queue_info.go` 的 `Reclaimable()`），无影响。
- `weight` 为 0 时补成 1：proportion 插件给这个队列分到的 deserved 是 0；所有队列都为 0 时会直接退出分配计算（`plugins/proportion/proportion.go:209`）。线上用的是 capacity 插件，不看 weight，影响不大，但还是建议显式写成 1。

## 4. 失去的校验

这些校验缺了不会马上出问题，但会把错误推迟到运行期。

- **jobs/validate**（`pkg/webhooks/admission/jobs/validate/admit_job.go`）：
  - 本来会在提交时直接拒绝这些错误：minAvailable 大于 replicas、task 重名、作业或 Pod 名超长、policy 的 event/action 写错、插件名不存在、task 依赖成环、Pod 模板不合法；
  - 本来会拒绝提交到不存在、非 Open、root 或非叶子的队列；
  - 本来会禁止更新 minAvailable、replicas、PriorityClassName 以外的字段。

  没有这层校验，这些错误要么让作业永久 Pending，要么让建 Pod 失败。
- **queues/validate**（`pkg/webhooks/admission/queues/validate/validate_queue.go`）：
  - default 和 root 队列、还有 Pod 的队列、有子队列的队列都能被直接删掉；
  - 层级队列的 parent、深度、子队列 deserved/guarantee 之和超过父队列、capability 超过祖先，这些都不再检查。
- **podgroups/validate**：不再检查 PodGroup 提交的队列是否 Open。不过 capacity 插件在调度时也会跳过非 Open 队列，作业只是一直 Pending。
- **hypernodes/validate、cronjobs/validate**：内部目前没用，可以忽略。

## 5. 内部分支的情况

- 内部分支从 base（`60a7f7536`）到 `origin/gpu-numa` 没有改过 `pkg/webhooks`，没有自定义 webhook 逻辑需要迁移。
- 线上开的 admission（`manifests/lfga-cluster/webhook-manager-deployment.yaml`）：

  ```
  --enabled-admission=/jobs/mutate,/jobs/validate,/podgroups/mutate,/pods/validate,/pods/mutate,/queues/mutate,/queues/validate
  ```

  社区默认没开的三个，去掉后的影响：

  | webhook | 作用 | 去掉的影响 |
  |---|---|---|
  | `pods/mutate` | 按 resourceGroups 给 Pod 注入 nodeSelector、亲和性、容忍、schedulerName | 内部 `volcano-admission.conf` 里 resourceGroups 是注释掉的，实际是空操作，无影响 |
  | `pods/validate` | 校验 Pod 上 budget 注解（min-available / max-unavailable）的格式 | 只是格式校验，影响小 |
  | `podgroups/mutate` | PodGroup 的 queue 等于 `default` 时，用 namespace 上的 `scheduling.volcano.sh/queue-name` 注解改写队列 | **如果靠 namespace 注解来决定作业进哪个队列，去掉后这个功能就没了** |

## 6. 建议

- **作业全部由上层组件（kuper-system）创建，而且能保证第 3 节表格里的字段都写全**：可以不部署。建议在上层组件里加一层等价的默认值填充和关键校验（队列存在且为叶子、minAvailable 不超过 replicas、task 名唯一），同时用 RBAC 给 Queue 的删除和修改收权限。
- **还有用户直接 `kubectl apply` 提交 vcjob 或 Queue**：建议保留 webhook-manager。它是无状态服务，内部也没有改动，直接用社区版即可。

### 6.1 在 k8s 1.19 上保留 webhook-manager 的注意点

- `jobs/validate` 用 k8s 1.35 版本的规则校验 Pod 模板，可能比 1.19 更严或者对新字段不认识。先在测试集群里拿线上真实的作业 yaml 做一轮 `kubectl create --dry-run=server` 验证。
- 有问题的话，可以只开 `jobs/mutate` 和 `queues/mutate,queues/validate`，暂时不开 `jobs/validate`。
- webhook-manager 启动时会调用 `SetupComponentGlobals`，同样不能传 kube 自带的特性门控，见 [v1.15-on-k8s-1.19.md](./v1.15-on-k8s-1.19.md) 2.1 节。
