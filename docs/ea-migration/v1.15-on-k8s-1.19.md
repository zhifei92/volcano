# Volcano v1.15 在 Kubernetes 1.19 上运行的可行性与改造清单

> 分析对象：社区 v1.15.3（`go.mod` 依赖 k8s.io/* v0.35.3、Go 1.25）。
> 本文是 `v1.9-to-v1.15-upstream-changes.md` 第 4 节的展开版，所有结论都对照 v1.15.3 源码核对过，emulation version（特性门控的模拟版本）机制做过实际运行验证（见 2.1 节）。

---

## 0. 前提：线上 apiserver 是 1.19（已确认）

已确认线上 apiserver 是 1.19，所以本文的所有问题都适用。

### 0.1 一个需要先解释清楚的矛盾

按代码看，**内部 fork 当前的 scheduler 在原生 1.19 apiserver 上会卡住启动**，和 v1.15 的问题完全一样：

- `origin/gpu-numa` 的 `pkg/scheduler/cache/cache.go:683-684`：门控 `PodDisruptionBudgetsSupport` 默认开启，注册 `policy/v1` 的 PDB informer；
- `cache.go:882-888`：`Run()` 中启动 informer 后调用 `WaitForCacheSync`（:921-923），而且没有超时；
- 仓库里的部署清单（`manifests/lfga-cluster`、`manifests/k8s-v121`）没有传 `--feature-gates`。

既然线上能正常运行，说明下面三种情况至少有一种成立。**它决定了 v1.15 的 M1 是否必须做**，请先确认：

| 情况 | 怎么确认 | 对 v1.15 的影响 |
|---|---|---|
| A. 线上 Deployment 实际传了 `--feature-gates=PodDisruptionBudgetsSupport=false`（仓库清单已过时） | `kubectl -n kuper-system get deploy volcano-scheduler -o jsonpath='{.spec.template.spec.containers[0].args}'` | 照搬这个参数即可，M1 已经有现成做法 |
| B. 内部的 1.19 apiserver 打过补丁，回移植了 `policy/v1`（JDOS 定制版） | `kubectl api-versions \| grep -E '^policy/'`、`kubectl get --raw /apis/policy/v1` | M1 可以不做。但还要再查有没有回移植其他 API（见 0.2），本文 2.2 节表格要按实际结果修正 |
| C. 线上镜像不是 `gpu-numa` 主干构建的 | 对比线上镜像 tag 和主干 commit；查看 scheduler 启动日志中有没有 `PodDisruptionBudget` 相关的 reflector 报错 | 先弄清楚线上实际运行的代码，迁移基线可能需要调整 |

### 0.2 建议在目标集群上一次性采集的信息

```bash
kubectl version -o yaml | grep -A6 serverVersion
kubectl api-versions | sort > api-versions.txt              # 和下面的列表对照
kubectl get --raw /openapi/v2 | grep -c x-kubernetes-validations   # >0 说明 CRD 的 CEL 被回移植了
ps -ef | grep kube-apiserver | tr ' ' '\n' | grep -E 'feature-gates|runtime-config|tls-cipher'   # 在 master 上执行
kubectl -n kuper-system get deploy -o yaml | grep -E 'image:|--feature-gates|--csi-storage'
```

需要重点关注 `api-versions.txt` 中有没有这些 API（原生 1.19 都**没有**）：`policy/v1`、`storage.k8s.io/v1beta1`（CSIStorageCapacity）、`resource.k8s.io/*`、`flowcontrol.apiserver.k8s.io/v1beta1`（1.20+）。

### 0.3 一个有利的证据

内部 fork 用的是 **k8s.io/client-go v0.30.2**（k8s 1.30 的客户端和调度插件库），已经在 1.19 apiserver 上稳定运行。这说明"新客户端加旧 apiserver"的组合在实际中是可行的。v1.15 的 client-go v0.35 比 v0.30 多出的风险，主要只有 WatchList（已分析，会回退）和队列状态使用 SSA（见 P4）两处。另外，内部 fork 没有用 SSA，所以 **SSA 在线上 1.19 上还没有被验证过**，P4 的优先级要提高。

### 0.4 原先的推测作废

之前推测"线上 apiserver 可能 ≥ 1.21，1.19 指的是 archimedes 依赖的 kube-scheduler 框架版本"，这个推测作废。archimedes 的问题仍然存在，但它是第 7 节说的编译期问题，和集群版本无关，两件事要分开处理。

## 1. 结论

**可行，代价可控。** 调度主链路（cache、session、allocate / preempt / reclaim / backfill、bind）在 1.19 上能正确运行。前提是：

1. **必做 3 项**，不做就无法安装或无法启动：
   - 关闭 PDB 门控（或打补丁回退到 `policy/v1beta1`）；
   - 安装前去掉 HyperNode CRD 中的 CEL 规则；
   - 保持 VAP / MAP 关闭（默认就是关闭的）。
2. **建议做的 5 个小补丁**（合计约 200~300 行），用来消除"静默卡死"和"静默失效"。
3. **接受一批功能在 1.19 上不可用**（DRA、调度门控、sidecar 等），这些功能内部目前都没有使用。

为什么"能跑"：Volcano v1.15 自己已经做了不少向下兼容：

| 兼容机制 | 位置 | 效果 |
|---|---|---|
| `SetupComponentGlobals` 把特性门控的 emulation version 设为 apiserver 版本 | `pkg/util/util.go:91`，scheduler 和 webhook-manager 启动时调用 | 所有 1.19 之后才引入的 kube 特性门控自动变为关闭（已实测，见 2.1） |
| CSIStorageCapacity 使用 `v1beta1` 且默认关闭 | `cache/cache.go:698-702`、`capabilities/volumebinding/volume_binding.go:616-622` | 不会去 LIST 1.19 上不存在的 API |
| DRA informer 只有在门控开启时才注册 | `cache/cache.go:831` | 在 emulation 1.19 下不会注册 |
| vc-agent 驱逐时先尝试 `policy/v1`，失败再用 `v1beta1` | `pkg/agent/utils/eviction/eviction.go` | 已兼容 |
| Volcano 自己的门控使用不带版本的 `Add` 注册 | `pkg/features/volcano_features.go:58` | 不受 emulation version 影响，行为和高版本集群一致 |

## 2. 关键机制

### 2.1 emulation version：为什么 DRA、sidecar、WatchList 会自动关闭

`SetupComponentGlobals` 从 discovery 读出 apiserver 版本（例如 `1.19`，也兼容 `1.19+` 这种厂商格式），把 kube 组件的有效版本注册为 1.19。`component-base` 的门控在查询时，会取"版本号 ≤ 1.19"的那条规格。1.19 之后才引入的门控找不到规格，就退回到 `Default: false, PreAlpha`。

已用 v1.15.3 依赖实际运行验证（程序在 `/tmp/vc115full/cmd/emucheck`）：

| 门控 | 默认（emulation 1.35） | `SetupComponentGlobals(1.19)` 之后 |
|---|---|---|
| kube `DynamicResourceAllocation` | true | **false** |
| kube `SidecarContainers` | true | **false** |
| kube `InPlacePodVerticalScaling` | true | **false** |
| kube `PodLevelResources` | true | **false** |
| kube `VolumeAttributesClass` | true | **false** |
| kube `NodeInclusionPolicyInPodTopologySpread`、`MatchLabelKeysInPodTopologySpread` | true | **false**（等于 1.19 的语义） |
| client-go `WatchListClient` | true | **false** |
| volcano `PodDisruptionBudgetsSupport` | true | **true**（不受影响，所以必须手动关闭） |

还要注意 3 点：

1. **controller-manager 没有调用 `SetupComponentGlobals`**，所以它的 client-go `WatchListClient` 仍然是 true。controller-manager 依赖了 `k8s.io/kubernetes/pkg/features`，这个包会把 client-go 的门控桥接到 `DefaultMutableFeatureGate`，因此 **`--feature-gates=WatchListClient=false` 对 controller-manager 有效**。即使不关，reflector 在 watch-list 请求出错后也会回退到普通 LIST（`client-go/tools/cache/reflector.go:428-434`）。1.19 的 apiserver 会拒绝带 `resourceVersionMatch` 的 watch 请求，所以只是每次重新 list 时多一次失败请求，不会卡住。
2. 在 emulation 1.19 下，**不要给 scheduler 和 webhook-manager 传任何 kube 自带的门控**（例如 `SidecarContainers=true`）。flag 先解析，`SetupComponentGlobals` 后执行，切换版本时会报 "not available before 1.2x"，进程直接启动失败。只传 Volcano 自己的门控。
3. 日志里会出现一批 `SetEmulationVersionAndMinCompatibilityVersion will change already queried feature:X from true to false` 的警告，这是预期行为。

### 2.2 informer 同步：唯一会"静默卡死"的地方

scheduler 启动时调用 `sc.WaitForCacheSync(stopCh)`（`cache/cache.go:860, 893-896`），对 kube 和 vc 两个 informer factory 都**没有超时**。只要有一个 informer 对应的 API 在 1.19 上不存在，或者对应的 CRD 没装，LIST 就会一直 404，调度循环永远不会开始，并且**进程不会退出、也不会报错**，只有 reflector 的重试日志。

v1.15.3 scheduler 注册的 informer，按在 1.19 上的可用性分类：

| informer | API | 1.19 | 条件 |
|---|---|---|---|
| Namespaces、Services、Nodes、Pods、PVC、PV、ResourceQuotas | core/v1 | ✅ | 无条件 |
| ReplicationControllers、ReplicaSets、StatefulSets | core/v1、apps/v1 | ✅ | `WorkLoadSupport`（默认开） |
| StorageClasses、VolumeAttachments、CSINodes | storage/v1 | ✅ | 无条件 |
| CSIDrivers | storage/v1 | ✅（1.18 GA） | `CSIStorage` 门控 + `--csi-storage` |
| PriorityClasses | scheduling/v1 | ✅ | `PriorityClass` 门控（默认开） |
| **PodDisruptionBudgets** | **policy/v1** | ❌ **1.21 才有** | **`PodDisruptionBudgetsSupport`（默认开）** |
| **CSIStorageCapacities** | storage/v1beta1 | ❌ 1.21 才有（1.19 只有 v1alpha1） | `CSIStorage`（默认关） |
| **ResourceClaims、ResourceSlices、DeviceClasses** | resource.k8s.io/v1 | ❌ 1.34 | kube DRA 门控（emulation 1.19 下自动关闭） |
| PodGroups、Queues | Volcano CRD | ✅ | 无条件 |
| Numatopologies | Volcano CRD | ✅ | `ResourceTopology`（默认开）：**CRD 必须安装** |
| HyperNodes | Volcano CRD | ✅ | **无条件：CRD 必须安装** |
| NodeShards | Volcano CRD | ✅ | 只有分片模式开启时注册 |

predicates 插件每个 session 通过 `ssn.InformerFactory()` 初始化 kube 的 in-tree 插件（interpodaffinity、podtopologyspread、nodevolumelimits、volumebinding）。用到的都是上表中 ✅ 的 informer，所以没有问题。

controller-manager 和 webhook-manager 用到的 kube API 全部在 1.19 上可用：core/v1、apps/v1、batch/v1、scheduling/v1、networking/v1（svc 插件创建 NetworkPolicy）、coordination/v1、admissionregistration/v1。

## 3. 必须做的改动（不做就无法安装或启动）

| # | 改动 | 方式 | 不做会怎样 |
|---|---|---|---|
| M1 | 关闭 PDB informer | scheduler 启动参数加 `--feature-gates=PodDisruptionBudgetsSupport=false`；调度配置里不要启用 `pdb` 插件（线上目前没有启用） | scheduler 卡在 `WaitForCacheSync`，永远不调度 |
| M2 | 去掉 HyperNode CRD 中的 CEL | 删掉 `topology.volcano.sh_hypernodes.yaml` 里 `x-kubernetes-validations` 那一段（第 139-146 行左右，只有这一处，其他 CRD 都没有） | Helm 和 kubectl 会按 1.19 的 OpenAPI 校验，报 unknown field，安装失败。如果用 `--validate=false` 强行安装，规则会被静默丢弃 |
| M3 | 不创建 VAP / MAP | Helm values 中保持 `vap_enable` / `map_enable` 为 false（默认值） | `admissionregistration.k8s.io/v1` 的 ValidatingAdmissionPolicy 要 1.30，MutatingAdmissionPolicy 要 1.34，创建会失败 |

另外几项是配置约束，默认就满足，**不要打开**即可：

- `CSIStorage` 门控和 `--csi-storage`：会去 LIST `storage/v1beta1` CSIStorageCapacity，1.19 没有，scheduler 会卡住。
- `SchedulingGatesQueueAdmission`：依赖 `spec.schedulingGates`（1.26+）。1.19 的 apiserver 会静默丢弃这个字段，功能失效但不报错。
- `capacity.DynamicResourceAllocationEnable`：DRA 在 1.19 不存在。
- Helm 中的 `service.ipFamilyPolicy` / `ipFamilies`（1.20+）：不要设置。
- 不要部署 `vc-agent` / `network-qos`（混部组件，依赖较新的 kubelet 和 cgroup 能力，没有评估过，内部也没有使用）。

## 4. 建议的代码补丁

| # | 补丁 | 位置 | 规模 | 解决什么问题 |
|---|---|---|---|---|
| P1 | 根据 discovery 结果选择 API 版本；PDB 回退到 `policy/v1beta1` | `pkg/scheduler/cache/cache.go`、`plugins/pdb/pdb.go` | ~100 行 | 不用关闭 PDB 功能也能在 1.19 上启动；以后再升级集群不用改配置 |
| P2 | `WaitForCacheSync` 加超时，并打印未同步的 informer | `cache/cache.go:893` | ~30 行 | 把"静默卡死"变成"明确报错退出"。**apiserver 已确认是 1.19，这一项必做** |
| P3 | controller-manager 也调用 `SetupComponentGlobals` | `cmd/controller-manager/app/server.go` `Run()` 开头 | ~5 行 | 三个组件的门控默认值保持一致，WatchList 自动关闭 |
| P4 | 队列状态 `ApplyStatus` 失败时回退到 `UpdateStatus` | `pkg/controllers/queue/queue_controller_action.go:106/133/164` | ~40 行 | 1.19 上 SSA 是 Beta（默认开）。如果集群关闭了 SSA，或者行为有差异，队列会一直停在空状态或旧状态。**内部 fork 从没用过 SSA，线上没有验证过，建议必做** |
| P5 | 在 webhook 中补回 HyperNode selector 校验 | `pkg/webhooks/admission/hypernodes/validate/admit_hypernode.go` | ~20 行 | M2 删掉 CEL 后，"exactMatch / regexMatch / labelMatch 必须且只能填一个"就没有校验了。不用 HyperNode 可以不做 |

### P1 示意

```go
// pkg/scheduler/cache/cache.go
func serverHasResource(dc discovery.DiscoveryInterface, groupVersion, resource string) bool {
	list, err := dc.ServerResourcesForGroupVersion(groupVersion)
	if err != nil {
		return false
	}
	for _, r := range list.APIResources {
		if r.Name == resource {
			return true
		}
	}
	return false
}

if utilfeature.DefaultFeatureGate.Enabled(features.PodDisruptionBudgetsSupport) {
	switch {
	case serverHasResource(sc.kubeClient.Discovery(), "policy/v1", "poddisruptionbudgets"):
		informerFactory.Policy().V1().PodDisruptionBudgets().Informer()
	case serverHasResource(sc.kubeClient.Discovery(), "policy/v1beta1", "poddisruptionbudgets"):
		informerFactory.Policy().V1beta1().PodDisruptionBudgets().Informer()
		sc.pdbUseV1beta1 = true
	default:
		klog.Warning("PodDisruptionBudget API not served, pdb plugin disabled")
	}
}
```

pdb 插件只用到 `Namespace`、`Spec.Selector`、`Status.DisruptionsAllowed`、`Status.DisruptedPods` 这几个字段（`plugins/pdb/pdb.go:64-126`），两个版本中都有。实现一个 `PodDisruptionBudgetLister` 适配器，把 v1beta1 对象转成 v1 对象即可。插件已经把"空 selector"当作不匹配任何 Pod 处理（:100-101），和 v1beta1 的语义一致，**不需要额外处理 selector 语义差异**。RBAC 规则按 `apiGroups: ["policy"]` 授权，和版本无关，不用改。

CSIStorageCapacity 可以用同样的方式：v1 → v1beta1 → 不注册。

### P2 示意

```go
func (sc *SchedulerCache) WaitForCacheSync(stopCh <-chan struct{}) {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Minute)
	defer cancel()
	go func() { select { case <-stopCh: cancel(); case <-ctx.Done(): } }()

	var unsynced []string
	for t, ok := range sc.informerFactory.WaitForCacheSync(ctx.Done()) {
		if !ok { unsynced = append(unsynced, t.String()) }
	}
	for t, ok := range sc.vcInformerFactory.WaitForCacheSync(ctx.Done()) {
		if !ok { unsynced = append(unsynced, t.String()) }
	}
	if len(unsynced) > 0 {
		klog.Fatalf("informers not synced (API not served or CRD missing?): %v", unsynced)
	}
}
```

## 5. 1.19 上不可用的功能（接受即可）

| 功能 | 需要的 k8s 版本 | 内部是否使用 |
|---|---|---|
| DRA（`resource.k8s.io/v1`） | 1.34 | 否 |
| `SchedulingGatesQueueAdmission`（`spec.schedulingGates`） | 1.26+ | 否 |
| sidecar 容器（`restartPolicy: Always` 的 init 容器）资源计算 | 1.28+ | 否。1.19 上也没有这种 Pod |
| 原地扩缩容、PodLevelResources | 1.27+ / 1.32+ | 否 |

| PDB 保护（关闭门控时） | — | 线上没有启用 `pdb` 插件，无影响；做 P1 后可以恢复 |

## 6. 需要实测确认的风险点

| 风险 | 说明 | 等级 | 如何确认或规避 |
|---|---|---|---|
| 超出 client-go 的版本偏差支持范围 | client-go 0.35 官方只承诺 ±1 个 minor，和 1.19 相差 16 个版本。用到的都是稳定 GA API，新客户端写老服务端的方向不会丢字段（新客户端结构体是超集，零值字段 omitempty） | 低 | e2e + 灰度 |
| 队列状态的 SSA | `ApplyStatus` 依赖 SSA。SSA 在 1.18 Beta 并默认开启，1.19 上 CRD status 的 apply 可以用。内部 fork 用的是 `UpdateStatus`，线上从没走过 SSA | 中 | 检查 apiserver 有没有 `--feature-gates=ServerSideApply=false`；创建队列后看 `.status.state` 是否变为 Open；或者做 P4 |
| in-tree 卷的 CSI 迁移假设 | k8s 1.35 的 nodevolumelimits / volumebinding 假设 in-tree 云盘（EBS、GCE PD、Azure Disk、Cinder、vSphere）已经迁移到 CSI，旧的非 CSI 卷数量限制插件已删除 | 低（自建 IDC 基本不用这些卷） | 不使用这些 in-tree 云盘就没有影响 |
| webhook 的 Pod 模板校验按 1.35 规则执行 | vcjob 的 webhook 用 k8s 1.35 的 core validation 校验 PodTemplate，个别 1.19 允许的写法可能被拒绝（高版本集群也是一样） | 低 | 用线上真实 vcjob 的 YAML 做一遍 dry-run |
| Go 1.25 的 TLS 和证书要求 | Go 1.18+ 拒绝 SHA-1 签名的证书，Go 1.22+ 客户端默认不使用 RSA 密钥交换的密码套件 | 低 | `openssl x509 -in apiserver.crt -noout -text | grep Signature`，确认是 sha256；确认 apiserver 没有把 `--tls-cipher-suites` 限制为只有 RSA 密钥交换 |
| 本 session 里新增的 informer | in-tree 插件在 session 内向 factory 请求的 informer，如果启动时没注册过，就不会被 Start，lister 返回空 | 低 | 当前用到的 informer 启动时都已注册（2.2 节表格）。以后新增 in-tree 插件时要注意 |

## 7. 和内部迁移的关系

- **archimedes 插件**：它依赖的是 k8s 1.19.9 的 kube-scheduler 框架（`pkg/scheduler/archimedes-scheduler`），而 v1.15 整个模块固定在 k8s 1.35。同一个 `go.mod` 里不可能同时有两套 `k8s.io/kubernetes`。这是**编译期**冲突，和集群版本无关，必须移植到 1.35 的 fwk 接口，或者拆成独立进程（例如 extender 或 sidecar 服务）。详见 `v1.15-feature-inventory.md` 第 2 节和 `scheduler-decoupling-proposal.md`。
- **内部 CRD**（Reservation、NRT 等）：都是 apiextensions/v1 CRD，迁移时同样要检查有没有 CEL、`selectableFields`（1.30+）这类新字段。
- **内部插件**：按照 01 文档和 07 文档的说明，确保 predicate 返回 `Unschedulable` 类的 code。这一点和 k8s 版本无关，但在 1.19 上同样适用。

## 8. 验证方案

1. **kind 1.19 冒烟测试**：使用 `kind v0.17.x` 加 `kindest/node:v1.19.16`。社区的 `hack/e2e-kind-config.yaml` 里有 DRA 和 MAP 的门控与 apiserver 参数，1.19 不认识，**需要另写一份去掉这些配置的 kind 配置**。然后运行：
   ```bash
   KIND_OPT="--config hack/e2e-kind-config-1.19.yaml --image kindest/node:v1.19.16" \
   E2E_TYPE=SCHEDULINGBASE ./hack/run-e2e-kind.sh
   ```
   依次跑 `SCHEDULINGBASE`、`SCHEDULINGACTION`、`JOBP`、`JOBSEQ`、`VCCTL`、`CRONJOB`。跳过 `DRA`、`SCHEDULINGGATES`、`ADMISSION_POLICY`、`HYPERNODE`（如果不用 HyperNode）。
2. **启动日志检查**（三个组件都要看）：
   - 有 `set feature gate emulationVersion to 1.19`（scheduler、webhook-manager；做了 P3 的话 controller-manager 也应该有）；
   - **没有**持续出现 `failed to list *v1.PodDisruptionBudget`、`*v1beta1.CSIStorageCapacity`、`resource.k8s.io` 之类的 reflector 错误；
   - scheduler 出现第一条 `Open Session` 日志，说明 cache 已经同步完成。
3. **功能验证**：gang、队列配额（capacity / proportion）、preempt、reclaim、backfill、PriorityClass、队列 Open / Close 状态切换（验证 SSA），以及 vcjob 的生命周期（创建、重启、完成后的 TTL 清理）。
4. **灰度**：先在一个小集群上把 v1.15 scheduler 用不同的 `schedulerName` 和 v1.9 并行运行，只接管测试队列。观察 1~2 周的调度延迟、bind 失败率和 apiserver 的 4xx 请求量。
