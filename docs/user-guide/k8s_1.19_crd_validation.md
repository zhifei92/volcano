# Kubernetes 1.19 下 HyperNode / Queue 的 CRD 校验说明

本文说明：在 Kubernetes 1.19 集群上部署 Volcano v1.16 时，为了兼容 1.19，我们移除了哪些 CRD 校验规则，移除后哪些校验仍然生效，以及**哪些设置必须由使用者自己保证正确**。

> **重要：** 下面列出的两类配置，在 1.19 集群上**不会被系统拦截**。如果写错，资源能正常创建，但调度结果可能与你的预期不一致。创建或修改 HyperNode、Queue 时，请按第 6 节的清单逐项检查。

## 1. 背景

Volcano v1.16 的 `hypernodes.topology.volcano.sh` 和 `queues.scheduling.volcano.sh` 两个 CRD，使用了 CEL 校验规则（`x-kubernetes-validations`）。CEL 规则在 Kubernetes 1.23 以 alpha 引入，1.25 进入 beta，1.29 才 GA。Kubernetes 1.19 不认识这个字段，apiserver 会忽略它，kubectl 的客户端校验也可能报 `unknown field`。

因此，1.19 部署时需要把这些规则从生成的 CRD 中剥离。剥离后，原来由 CEL 规则保证的校验就没有了。剥离通过生成流程的开关完成（见第 3 节），源码中的 `+kubebuilder` 标记保持不变，社区版本的生成结果也不受影响。

另外，仓库中的 ValidatingAdmissionPolicy（VAP）同样不可用：它依赖 `admissionregistration.k8s.io/v1`，该版本在 Kubernetes 1.30 才 GA。1.19 上请保持 `custom.vap_enable: false`（helm chart 默认值即为 false）。

## 2. 被移除的校验

| 资源 | 字段 | 原规则 | 含义 |
|---|---|---|---|
| HyperNode | `spec.members[].selector` | `has(exactMatch) \|\| has(regexMatch) \|\| has(labelMatch)` | 至少设置一种选择器 |
| HyperNode | `spec.members[].selector` | `(has(exactMatch)?1:0) + (has(regexMatch)?1:0) + (has(labelMatch)?1:0) <= 1` | 三种选择器最多设置一种 |
| Queue | `spec.allowedNamespaces` | `!self.exists(x, x == '*') \|\| size(self) == 1` | 通配符 `*` 只能单独出现 |

以上规则在 `v1.16.0` 社区版的 CRD 中就存在。规则的源头是 `staging/src/volcano.sh/apis` 中的 `+kubebuilder:validation:XValidation` 标记，CRD 由 controller-gen 生成。涉及的生成文件：

- `config/crd/volcano/bases/topology.volcano.sh_hypernodes.yaml`
- `config/crd/volcano/bases/scheduling.volcano.sh_queues.yaml`
- `installer/helm/chart/volcano/crd/bases/topology.volcano.sh_hypernodes.yaml`
- `installer/helm/chart/volcano/crd/bases/scheduling.volcano.sh_queues.yaml`
- `installer/volcano-development.yaml`

这些文件**不手工修改**。它们保持社区原样，由生成流程产出。

## 3. 生成 1.19 部署文件

使用 `CRD_STRIP_CEL=true` 开关生成：

```bash
make generate-yaml TAG=v1.16.0-k8s119 CRD_STRIP_CEL=true
```

- 剥离只作用于 `generate-yaml` 最终生成的单个 YAML 文件（`hack/generate-yaml.sh` 调用 `hack/strip-cel-validations.sh`）。`config/crd/*/bases` 和 `installer/helm` 下的 CRD 保持社区原样，源码和社区的生成文件都不会被修改。
- 产物有两份：
  - `_output/release/volcano-v1.16.0-k8s119.yaml`：完整的部署文件，包含 CRD、webhook、controller、scheduler 等。`_output/` 在 `.gitignore` 中，不会提交，需要留存时请由发布流程归档。
  - `config/crd/volcano/k8s119/`：12 个已去掉 CEL 的 CRD（含 jobflow 的两个），可单独 `kubectl apply -f config/crd/volcano/k8s119/`。该目录与 `bases/`、`v1beta1/` 并列，**会提交到仓库**。可用 `CRD_STRIP_DIR=<目录>` 改输出位置。
- `k8s119/` 只在带 `CRD_STRIP_CEL=true` 时才会更新，CI 不检查它。修改了 API 的 `+kubebuilder` 标记或升级 controller-gen 后，需要重新执行上面的命令并提交 `k8s119/` 的变化，否则它会落后于 `bases/`。
- TAG 请使用与社区不同的名称，避免覆盖正式产物。
- 默认 `CRD_STRIP_CEL=false`，此时 `make generate-yaml` 与 CI 的 `verify-generated-yaml` 生成的结果完全一致。
- 生成器版本必须与 Makefile 一致（`controller-gen` v0.20.0）。`manifests` 调用的是 PATH 中的 `controller-gen`，只有找不到时才会按 v0.20.0 下载。PATH 中是其他版本时，生成的注解版本会变（例如 v0.17.2），`config/crd` 下所有文件都会出现无关改动。

## 4. 仍然生效的校验

以下校验在 1.19 上仍然有效，不需要额外处理。

**由 apiserver 通过 OpenAPI schema 校验（1.19 支持）：**

- HyperNode `exactMatch.name`：必填，长度至少 1，且符合 DNS 名称格式（`pattern`）。
- HyperNode `regexMatch.pattern`：必填，长度至少 1。
- HyperNode `members[].type`：只能是 `Node` 或 `HyperNode`。
- HyperNode `tier`：整数。
- Queue 等资源的其他字段类型、枚举值等 schema 约束。

**由 Volcano 的 validating webhook 校验（需要 webhook 正常运行）：**

- HyperNode 至少包含一个 member（`validateHyperNode`，`pkg/webhooks/admission/hypernodes/validate/admit_hypernode.go`）。
- HyperNode `regexMatch.pattern` 能被正则引擎编译。

webhook 只有在 `/hypernodes/validate` 已启用且 webhook 进程正常运行时才会生效。helm 默认的 `enabled_admissions` 已包含该路径，`failurePolicy` 为 `Fail`。

## 5. 需要使用者自己保证的设置（重点）

下列设置，**1.19 上没有任何系统校验**，需要使用者自己保证正确。

### 4.1 HyperNode：每个 member 只能设置一种选择器

每个 member 的 `selector` 只能设置 `exactMatch`、`regexMatch`、`labelMatch` 中的**一个**。

- **同时设置多个**：资源可以正常创建。调度器会把各个选择器匹配到的节点取**并集**，不会报错。结果是 member 包含的节点比你预期的多。
- **一个都不设置**：资源可以正常创建。该 member 不匹配任何节点，同样不报错。

示例（错误写法，1.19 上会被接受）：

```yaml
apiVersion: topology.volcano.sh/v1alpha1
kind: HyperNode
metadata:
  name: rack-1
spec:
  tier: 1
  members:
  - type: Node
    selector:
      exactMatch:
        name: node-1
      regexMatch:          # 错误：与 exactMatch 同时设置，结果是两者取并集
        pattern: "^node-.*"
```

正确写法：每个 member 只保留一种选择器。

```yaml
  members:
  - type: Node
    selector:
      exactMatch:
        name: node-1
```

### 4.2 Queue：通配符 `*` 必须单独出现

`spec.allowedNamespaces` 中如果包含 `*`，它必须是**唯一的一项**。

- **`["*", "team-a"]`**：资源可以正常创建。调度器遇到 `*` 就放行所有 namespace，`team-a` 这一项实际不起作用。写的人如果以为只放行 `team-a`，就会误判权限范围。
- **`[]`（空列表）或不设置**：表示不允许任何 NamespaceQueue 挂到该 Queue 下。这是 CRD 的既有语义，不会因为 CEL 删除而改变。

正确写法：

```yaml
spec:
  allowedNamespaces:
  - "*"        # 单独一项，表示允许所有 namespace
```

或者：

```yaml
spec:
  allowedNamespaces:
  - team-a
  - team-b
```

### 4.3 不要依赖 VAP 或 CEL 兜底

1.19 上这两类机制都不可用。即使你在其他集群上见过相关报错，也不要期待 1.19 上会出现同样的拦截。

## 6. 使用者检查清单

创建或修改 HyperNode、Queue 后，请执行以下检查。

**检查 1：每个 HyperNode member 只设置了一种选择器。**

```bash
kubectl get hypernodes -o json | jq -r '
  .items[] | .metadata.name as $n | .spec.members[]? |
  select(([.selector.exactMatch, .selector.regexMatch, .selector.labelMatch]
          | map(select(. != null)) | length) != 1) | $n'
```

输出为空表示通过。输出的名称是存在问题的 HyperNode，需要人工检查。

**检查 2：Queue 的 `*` 只单独出现。**

```bash
kubectl get queues -o json | jq -r '
  .items[] | select(.spec.allowedNamespaces != null
                    and (.spec.allowedNamespaces | index("*")) != null
                    and (.spec.allowedNamespaces | length) > 1) | .metadata.name'
```

输出为空表示通过。

**检查 3：确认 HyperNode 校验 webhook 已注册。**

```bash
kubectl get validatingwebhookconfigurations | grep -i volcano
kubectl get validatingwebhookconfigurations -o yaml | grep -n "hypernodes/validate"
```

如果没有输出，说明 HyperNode 的 Go 校验没有生效，member 数量和 regex 编译的检查都不会执行，需要人工确认配置。

**检查 4：确认没有开启 VAP。**

```bash
kubectl get validatingadmissionpolicies 2>&1 | head -1
```

1.19 上应返回资源类型不存在的错误。如果 VAP 资源存在，说明安装时误开了 `vap_enable`，需要检查 helm values。

## 7. 维护注意事项

- **剥离只在输出文件上进行，重新生成不会影响源 CRD。** 剥离由 `CRD_STRIP_CEL` 开关控制。默认关闭，所以 `make manifests`、`make generate-yaml` 和 CI 校验都保持社区原样；生成 1.19 文件时带上 `CRD_STRIP_CEL=true` 即可。
- **不要手工删除生成文件里的 CEL 规则。** 手工修改会被下一次生成覆盖，并导致 CI 的 `verify-generated-yaml` 失败。
- **源码注释已同步。** `pkg/webhooks/admission/hypernodes/validate/admit_hypernode.go` 和对应测试中的注释已经说明：互斥和必填校验依赖 CEL（Kubernetes >= 1.29）；在 1.19 上需要使用者自己保证，以本文为准。
- **升级 Kubernetes 后应恢复规则。** 集群升级到 1.29 或更高版本后，可以恢复这些 CEL 规则，由 apiserver 重新负责互斥和通配符校验。恢复前，本文第 5 节的设置仍需人工保证。
- **代码注释需要以本文为准。** `pkg/webhooks/admission/hypernodes/validate/admit_hypernode.go` 中的注释写着"互斥、必填等校验由 CRD 的 x-kubernetes-validations 和 VAP 负责"。在 1.19 上这一说法不成立，以本文为准。

## 8. 验证状态

本文的结论基于代码和 CRD 文件的静态分析。剥离脚本已在 5 个 CRD 文件上验证，输出与手工删除的结果一致；`make generate-yaml TAG=v1.16.0-k8s119 CRD_STRIP_CEL=true` 已在本机运行过，输出的 `_output/release/volcano-v1.16.0-k8s119.yaml` 中没有 CEL 规则。生成器已统一为 Makefile 指定的 controller-gen v0.20.0，`config/crd` 重新生成后与仓库版本完全一致，默认 `verify-generated-yaml` 也通过。截至编写时，**尚未在 Kubernetes 1.19 集群上做实际部署验证**。上线前建议：

1. 用 `kubectl apply --dry-run=server` 和 `kubectl apply --validate=strict` 分别应用修改后的 CRD，确认没有报错。
2. 创建一个同时设置两种选择器的 HyperNode，确认 apiserver 确实接受它（验证本文第 4.1 节的描述）。
3. 创建 `allowedNamespaces: ["*", "x"]` 的 Queue，确认被接受（验证第 4.2 节）。
